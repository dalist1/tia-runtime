# Atomic runtime upgrade plan

**Status:** implemented and offline-validated in disposable roots (see [Implementation status](#implementation-status)). Machine-local deployment records are retained privately. The human review gate is still open. This plan remains the acceptance contract for v0.7.0.

## Goal and guarantee

An upgrade must either leave the currently selected TIA runtime usable, or switch the dispatcher to one complete, verified new generation. Pi package versions, full and slim executables, build metadata, Jiti companion, model catalog/API chunks, FFF extension and dependencies, fast-tool helpers, and resource-loading adapters must be selected as one immutable generation. No process may combine files from two releases because an installer overwrote shared paths during its lifetime.

The transaction boundary is a single atomically renamed `current` symlink. Build, validate, and seal occur before the rename. Before that commit point, failure leaves the old selection and old launchers unchanged. After the commit point, a failed durability/health check reports that the new selection committed; it must not claim rollback. Explicit rollback creates a new activation selecting a retained older immutable generation. Old generations are not automatically deleted: active Pi processes and custom resources may still depend on them.

This is crash consistency on supported local Linux filesystems with same-filesystem atomic rename and working `fsync`, not protection against disk/device failure, malicious root, hostile writable parents, unsupported network filesystems, or power-loss behavior the filesystem does not provide.

## Paths and ownership

- `${TIA_ROOT}/generations/<uuid>/`: self-contained, read-only runtime generations.
- `${TIA_ROOT}/activations/<uuid>/`: immutable activation records and symlinks into exactly one generation (or a recorded legacy launcher during migration).
- `${TIA_ROOT}/current`: the sole activation selector; replace by same-filesystem temporary symlink plus rename.
- `${TIA_ROOT}/logs/`: mode-0600 transaction logs; never contain credentials or request bodies.
- `${TIA_ROOT}/.upgrade.lock`: exclusive `flock` spanning package resolution through activation; installer, rollback, verify, uninstall, and pruning serialize on the same lock.
- `${TIA_ROOT}/pi-agent/`: durable, mutable user state. Credentials, settings, models, keybindings, trust, sessions, databases, and other state must not be inside an immutable generation or recursively copied over on upgrades.
- `${TIA_ROOT}/packages/`: downloaded, version-locked package inputs only if they are verified immutable and included in generation provenance. Prefer installing the complete package set inside the staging generation.
- `${TIA_CMD_PATH}`: a stable, version-aware dispatcher. Install/upgrade may replace an existing TIA launcher only after identifying and retaining an exact byte-verified copy of the old TIA launcher. Never overwrite an unrelated command.
- Host/global Pi packages, shell settings/auth files, project files, running processes, services, and user extensions are outside installer ownership and must not be mutated.

Use same-filesystem staging under `generations/`. Validate every destination against its expected root, reject symlink-substituted transaction paths, and use restrictive permissions. Avoid hard links to mutable package-manager caches: a shared inode defeats generation immutability. Copy package files into the generation or use a separately content-addressed, read-only dependency store whose closure and integrity are verified.

## Mutable state and extensions

Persisted Pi state survives upgrades and rollback. `auth.json`, settings, models, keybindings, trust, sessions, session directories, FFF search/history databases, and shell-owned settings retain their current paths and bytes. Generation-specific transient data must not be shared across generations in a way that can mix code. Sealed generations are read-only, so runtime caches cannot live inside them: package-manager temp data exists only during staging, and Jiti's transform cache (`$TMPDIR/jiti`) keys each entry by the absolute source path and validates it against a source hash, so generation-private extension paths already keep entries generation-specific. Keep native helpers, `NODE_PATH`, Pi package/assets, slim catalogs/chunks, and bundled extension dependencies generation-specific.

Preserve installed user extensions. Preserve a customized `fast-tools.ts` by default only when its origin/hash is known to be user-owned; otherwise present a fail-closed choice or require `TIA_PRESERVE_FAST_TOOLS=1`. Never silently copy an extension `node_modules` symlink back to a global/shared package set. Validate each preserved extension's dependency resolution against the generation's exact Pi API and dependency closure. Maintain the stable logical extension identity/settings selection while making its immutable generation copy available to the loader. If a custom extension cannot be made generation-isolated, block activation and identify the exact extension; do not silently disable it or load dependencies from mutable global paths.

Resolve FFF's configured source/version from current installed state unless the user explicitly overrides it. Install and validate its complete dependency graph in staging. Preserve only mutable FFF databases and configuration across versions, not installed FFF code or native module symlinks.

## Transaction phases

1. **Preflight:** validate action/environment and platform; resolve absolute root; acquire nonblocking exclusive lock; inspect current selection, dispatcher, and prior manifest; reject unrelated launchers, malformed pointers, dirty external package inputs, and unsafe/symlinked paths. Record active activation, hashes, settings/auth/extensions fingerprints (never contents), filesystem/device IDs, runtime/compiler versions, chosen package/FFF versions, and source provenance.
2. **Select inputs:** resolve package versions deterministically. Without an explicit pin, the Pi version is the host Pi (Bun global `@earendil-works/pi-coding-agent`, as used by the `pi` command) so TIA and Pi stay synchronized; only when no host Pi exists is `latest` used, meaning the newest publish date across registry channels, with exact selected versions saved. The complete synchronized Pi package set must be installed privately in staging. Verify every runtime package version and dependency edge. Never update global packages. Validate runtime asset manifest/signatures/hashes before use. Network errors, schema/closure mismatch, unresolved channel, or unsupported platform stop here with old selection intact.
3. **Stage closure:** create a fresh generation; install Pi and all required packages into it; build full Pi, Jiti snapshot, slim stream and catalogs, FFF, fast tools, runtime-resource adapters, launch/control scripts and assets only within staging. Record exact versions, binary/module/API source hashes, build options, environment constraints, package dependency tree, native ABI/platform, asset manifest, and transformation fingerprints. No mutable `current` paths or user state are edited.
4. **Validate staged generation:** verify exact dependency versions and closure; reject symlinks/hardlinks that escape or alias mutable stores; compile/smoke both full and slim modes; exercise OAuth resolution with dummy credentials and an offline local SSE endpoint; exercise read/write/edit/bash and any required FFF/search contracts; verify resource/session paths resolve to preserved user state; require empty unexpected stderr, successful completion, exact output and verified file bytes; validate package identity and all runtime/catalog/API assets. Repeat checks after sealing using the exact launcher environment.
5. **Seal:** compute an inventory of every generation entry (relative path, type, mode, link target, file hash and size); seal immutable files/directories read-only; flush the generation filesystem with `syncfs(2)` (`sync --file-system`; per-file `fsync` of ~17k package files took ~160 s on ext4 with the same guarantee); write and sync a versioned manifest; verify the sealed tree against the manifest. No package-manager or build process may still be running.
6. **Prepare dispatcher/activation:** create a new immutable activation record linking exactly one generation, and stage a new stable dispatcher only when required. Preserve the previous activation/launcher as a verified rollback target. `fsync` activation files/directories and the root before switching.
7. **Commit:** compare-and-swap against the preflight activation; create a temporary relative symlink to the new activation; `fsync` root; atomically rename over `current`; `fsync` root again. The rename is the commit point. Do not edit the target generation after this point.
8. **Post-commit verification:** launch through the stable dispatcher, verify status/version/manifest/hash, run short isolated full and slim loopbacks, verify user-state and extension hashes, and record the activation. If any check fails, clearly report the committed generation and offer/perform a separately journaled atomic rollback to the verified previous activation. Do not turn post-commit errors into “install failed; old runtime still active.”
9. **Recovery:** on startup/status/next install, inspect transaction logs, `current`, activation records and generation manifests. A temp symlink or unreferenced staging directory is not active and can be quarantined/removed only after the lock and ownership checks. If current is corrupt, stop and name the verified previous activation; never guess a target. An interrupted pre-commit transaction leaves the pointer unchanged. An interrupted post-rename transaction is recognized as committed from `current` and verified before reporting.
10. **Rollback/prune/uninstall:** rollback verifies the target generation and atomically writes a new activation record/pointer; never edit an old generation in place. Uninstall first atomically selects a retained deactivated/tombstone activation while preserving state and old generations; remove launcher only with explicit policy and only after durable deactivation. Pruning is a separate explicit operation: retain current, previous, and operator-selected generations; prove no running process holds a generation before optional deletion, and never follow symlinks outside the runtime root.

## Stable launcher and already-running processes

The dispatcher reads one activation pointer per invocation, then `exec`s the immutable generation launcher. Full Pi and slim Pi must both use that generation's package/assets/catalogs/extensions/helpers. The selected generation is pinned for the whole process; running Pi sessions do not change runtime halfway through. Do not resolve `current` independently for each dependency after launch. Include generation-specific runtime paths in `PI_PACKAGE_DIR`, `NODE_PATH`, Jiti/cache paths, FFF module/native lookup, worker assets, and child process environment. Stable mutable state paths may be shared only where Pi's file-lock/atomic-write contracts support concurrent old/new processes.

## Fault-injection and acceptance tests

Use disposable roots, private package fixtures, local loopback only, dummy credentials, telemetry disabled, and preserved host state. Add deterministic failpoints at every transaction phase, including after each package install, asset/build output, FFF install, full/slim compile, each smoke check, each file/manifest fsync, dispatcher preparation, before pointer rename, immediately after pointer rename, post-commit verification, rollback, and uninstall. Exercise exceptions, timeouts, SIGTERM and SIGKILL; inspect the filesystem after a fresh process starts.

For every pre-commit failure assert: old `current` bytes/target unchanged; old launcher works; user settings/auth/session/extension/database hashes unchanged; no temp package process remains; staged partials are unselected and recoverable; logs identify the phase without secrets. For commit-boundary failures assert that pointer selection alone decides whether old or new generation is active, and both targets verify. Test cross-filesystem/rename denial, corrupt manifests/binaries, mismatched package versions, symlink/hardlink escapes, hostile env paths, concurrent installer/rollback, missing network, registry/FFF failure, resource-transform drift, running old sessions, and recovery of interrupted journals. Verify rollback repeatedly and verify rollback itself is crash-safe.

Run the normal gates (`bash -n install.sh scripts/install-tia.sh test.sh`, format, lint, typecheck, unit tests, full integration), plus full+slim+tool+FFF loopback through a sealed generation. Retain exact configs, full sanitized logs, hashes, tool/file receipts, failpoint result matrix, and build manifests. Then upgrade a disposable existing 0.6.0 installation with custom routing/fast-tools extensions and real-shaped settings/sessions, verify exact preservation, exercise a live old-generation process across activation, roll back, and repeat install.

## Release and rollout gates

- Keep atomic-generation installation opt-in until unit/fault-injection and disposable end-to-end gates pass.
- Install into a fresh isolated root and a copy of the prior 0.6.0 root; never use the live root as a test fixture.
- Review generated permissions, filesystem/device assumptions, manifests, rollback receipts and dispatcher diff.
- Only after a fresh isolated upgrade + post-commit verification + rollback pass may a release claim “fully atomic.”
- For the user's runtime: save a private pre-upgrade receipt/backup outside the active symlink targets; verify the active activation and settings/extensions hashes; install the pinned Pi/FFF versions into a new immutable generation; confirm status, hashes, full/slim mode and real custom extensions; keep the old generation as rollback. Never update global packages or remove historical generations during this operation.

## Implementation status

Single status record for this migration (2026-09-29). "Offline-tested" means disposable roots, loopback providers and dummy credentials; nothing below was run against the live `~/.local/share/tia` root.

**Implemented** in `scripts/runtime-{store,build,manager,control,smoke,resources,bootstrap}.ts`, `scripts/runtime-launch.sh` and `scripts/install-tia.sh`:

- Generations: private Pi package set and FFF closure installed with `--backend=copyfile` (no cache hardlinks) from recorded text lockfiles (`--lockfile-only` then `--frozen-lockfile` for FFF); exact version checks for all eight Pi packages and both FFF packages; resource-isolation transforms that fail closed on upstream drift; inventory with type/mode/size/hash/link target; rejection of dangling, escaping or hard-linked entries; read-only seal flushed with `syncfs`.
- Transaction: preflight recovery, launcher identification and activation verification; build → seal → validate the **sealed** tree through its own launcher (full JSON + read/write/edit/bash + FFF find/grep + slim stream) → re-verify inventory → dispatcher → activation → pointer rename → post-commit status + full/slim smoke through the stable dispatcher. Post-commit failures are reported as `COMMITTED` with the retained previous activation, never as rollback. A failed pre-commit transaction removes its own unselected activation and staging generation.
- User state: HMAC fingerprints (per-transaction key, never contents) before/after; extension changes during a build abort before commit; other state changes by running Pi processes are logged, not attributed to the installer. Launcher keeps legacy agent-dir semantics but never replaces or deletes user-owned regular credential files.
- Provenance: `fast-tools.ts` is replaced silently only when its hash matches a TIA-shipped version (all 21 historical hashes are in `runtime-assets.json`) or was explicitly preserved by a retained generation; otherwise install stops until `TIA_PRESERVE_FAST_TOOLS=0|1` is chosen. User extensions (including symlinked ones) are snapshotted into the generation with source link and tree hash recorded.
- Launcher/processes: the dispatcher reads `current` once and `exec`s one immutable launcher; full and slim modes get generation-pinned `PI_PACKAGE_DIR`, `NODE_PATH`, extension and native-helper paths regardless of inherited values. The shell installer runs the transaction in its own session and kills the whole process group on exit, so no package/build/smoke process survives a failed install.
- Recovery/control: temp pointers and unreferenced staging are removed under the lock unless a live process still uses them; a corrupt pointer is never guessed (verified activations are listed for explicit `control select <id>`). `tia rollback|verify|generations|recover|prune|uninstall` serialize on `.upgrade.lock`. `prune` is a dry run unless `--apply`, keeps current, the previous distinct runtime and `--keep=` generations, and skips generations referenced by any process's exe, maps, cwd or `TIA_GENERATION_DIR`. `uninstall` selects a tombstone activation and retains launcher, generations and state.
- Host Pi sync: without `TIA_PI_PACKAGE_VERSION`, the installer builds exactly the host Pi version (source recorded as `host`). Each launch compares the host `package.json` version with the generation (a bash file read, no fork); on mismatch it starts one background `tia sync --background` transaction per host version (log `logs/sync-<version>.log`), so running sessions keep their generation and the next launch uses the synchronized one. `tia sync` runs the same transaction in the foreground with a clean environment (only `TIA_PRESERVE_FAST_TOOLS` and proxy settings pass through). Pinned, `PI_PACKAGE_DIR` or latest-by-date installs and `TIA_AUTO_SYNC=0` never auto-sync. Slim mode reads the same TIA agent directory as full mode unless `PI_CODING_AGENT_DIR` names another one.
- Legacy migration: a v0.6.0 launcher is recognised only by its exact root, retained byte-for-byte under `legacy/`, and selected by a legacy activation before the dispatcher replaces it; rollback to it re-verifies its hash.

**Offline-tested** (evidence: [`bench/history/atomic-runtime-v1`](bench/history/atomic-runtime-v1/README.md)):

- `scripts/runtime-transaction.test.ts`: throw, SIGTERM and SIGKILL at each of 16 transaction phases (48 crashes) with pointer, launcher, user-state, recovery and log-secrecy assertions; orphaned staging process; legacy migration interrupted after dispatcher replacement; unrelated/symlinked/foreign launchers; tampered, hard-linked and escaping generations; corrupt pointer repair; crash-safe rollback; lock serialization; prune with a live holder.
- `scripts/runtime-launch.test.ts`: host-Pi version precedence, one-shot background sync, opt-outs, clean `tia sync` environment, generation pinning under hostile env values, slim routing, credential-link semantics, update blocking, FFF state repair, `fast-tools.ts` provenance policy, resource-transform drift.
- `scripts/runtime-fault-matrix.ts` (`bun run test:faults <new-dir>`): the real installer (real packages, compile and smoke) killed/failed at every phase, plus unknown Pi/FFF versions, unreachable registry and an external SIGTERM to the shell installer.
- `test.sh` (14 stages, disposable HOME; stage 14 bumps a host Pi manifest from 0.87.1 to 0.99.1 and requires one ordinary launch to produce a verified 0.99.1 generation in the background): full/slim/tool/FFF/OAuth/RPC/bootstrap checks through a sealed generation, and a v0.6.0 installation with a symlinked custom extension, customized `fast-tools.ts` and real-shaped settings/sessions upgraded (fail-closed refusal, explicit preservation, byte-identical user state), a live legacy session and a live generation session each answering across activation changes, rollback to byte-identical legacy `tia status`, and reinstall.

**Not covered / remaining blockers:**

- Human review gate still open: generated permissions, manifests, rollback receipts and the dispatcher diff.
- Not exercised: cross-filesystem/rename denial (only asserted in preflight via device IDs), fsync/syncfs failure injection, power loss, non-ext4 filesystems, non-Linux platforms.
- Auto-sync is not retried after a failed attempt for the same host version (for example, a `fast-tools.ts` edit that needs a new preservation choice); the launcher reports it on an interactive terminal and `tia sync` retries.
- Old generations are never deleted automatically; users must run `tia prune --apply`. Editing an extension in `pi-agent/extensions` takes effect at the next install or sync, because each generation holds an immutable snapshot.
